Module 03 // Deep Dive Mechanics

Token Bucket & Leaky Bucket: Capacity, Empty/Full States & Shaping

Tune bucket capacity ($C$), refill/outflow rate ($R$), and test edge conditions: drain the Token Bucket to empty (HTTP 429 immediately) or saturate the Leaky Bucket queue to full (HTTP 429 overflow).

Bucket Capacity ($C$) 6 units

Max burst tokens (Token Bucket) or max FIFO queue slots (Leaky Bucket).

Refill / Outflow Rate ($R$) 2.0 / sec

Sustained token generation rate or constant queue drain rate.

Continuous Client Arrival 1.5 req/s

Background steady traffic sent simultaneously into both pipelines.

1. Token Generation & Capacity ($C$)
tokens = min(C, prev + Δt × R)

Tokens accumulate at rate $R$ up to ceiling $C$ (excess tokens beyond $C$ are discarded). Computed lazily on request arrival using timestamp delta $\Delta t$—no background timers needed.

2. Handling Empty or Full Buckets
  • Token Bucket Empty (tokens < 1): Request is immediately rejected (HTTP 429). No queueing occurs.
  • Leaky Bucket Full (queue == C): Incoming packet overflows and is dropped (HTTP 429), while existing queued items continue draining at rate $R$.
3. Traffic Policing vs. Shaping
  • Policing (Token Bucket): Zero queueing delay; drops excess immediately. Passes bursts up to size $C$ to downstream services.
  • Shaping (Leaky Bucket): Delays excess packets in a FIFO queue to emit a flat, constant rate $R$, protecting fragile backends at the cost of latency.

              Redis Basics & Why Atomicity Works
              Single-Threaded Event Loop
            

            
    
              
  • In-Memory Speed + Native TTL: Redis stores counters in RAM (~0.5ms latency) and auto-cleans expired keys via EXPIRE / PEXPIRE, preventing memory leaks.
    • 
              
  • Single-Threaded Command Execution: Redis processes one command (or one Lua script) at a time on its main thread—eliminating lock contention and interleaving.
    • 
              
  • Why INCR Alone Isn't Enough: Running INCR followed by EXPIRE as two separate calls can leak permanent keys if the app crashes mid-flight; wrapping logic in EVALSHA makes multi-step checks 100% atomic.
    • 
            

          


          

            

              Production Redis Lua Token Bucket Script
              
            

            
-- KEYS[1] = bucket_key | ARGV = {capacity, refill_rate, now_sec, requested}
local data = redis.call("HMGET", KEYS[1], "tokens", "last_refill")
local tokens = tonumber(data[1]) or tonumber(ARGV[1])
local last = tonumber(data[2]) or tonumber(ARGV[3])
local filled = math.min(tonumber(ARGV[1]), tokens + (tonumber(ARGV[3]) - last) * tonumber(ARGV[2]))
local allowed = filled >= tonumber(ARGV[4]) and 1 or 0
if allowed == 1 then filled = filled - tonumber(ARGV[4]) end
redis.call("HMSET", KEYS[1], "tokens", filled, "last_refill", ARGV[3])
redis.call("PEXPIRE", KEYS[1], math.ceil((tonumber(ARGV[1]) / tonumber(ARGV[2])) * 2000))
return {allowed, math.floor(filled)}

Observability & Graceful Degradation Playbook:

            

              
• Alerting Signals: Track 429 spike ratio per route (detects retry storms) and Redis p99 > 5ms.

              
• Aggressive Timeouts: Cap Redis socket timeout at 5–10ms so a hung cache never stalls API worker threads.

              
• Circuit Breaker + Local Fallback: Trip circuit open on consecutive errors and fall back to a conservative in-memory limiter.

              
• Client Retry Discipline: Clients must honor Retry-After + exponential backoff with jitter to avoid thundering herds.
